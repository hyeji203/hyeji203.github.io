PROJECT 01

도와줘, 맵! (SafeMate)

가로등과 사용자 제보로 밤길 위험도를 계산해, 최단경로와 안심경로를 함께 안내하는 웹 지도 서비스

기간
2026.09 ~ 2026.11
인원
3인 팀
역할
지도·경로 탐색 담당 (지도 데이터 가공, 경로 계산 서버, 지도 화면)
스택
React · Spring Boot · MySQL · WebSocket · Python
GitHub

Backend 포인트

  • 같은 다익스트라에 비용 함수만 바꿔 최단경로와 안심경로를 한 번에 계산
    안심 비용 = 도보 비용 × (1 + 2.0 × 위험도)
  • 도로 종류별 보행 비용 설계 (보행자길 0.9배 ~ 큰 차도 2.0배, 계단 2.5배)
  • 보고 있는 경로 50m 안에 새 제보가 들어오면 안심경로를 실시간으로 다시 찾고, 그동안 기존 경로 유지
  • 출발·도착이 지하철역이면 가장 빠른 출구(계단/에스컬레이터)로 안내
  • 카카오 로컬 API 키를 서버에만 두고 장소 검색 API 제공

Frontend 포인트

  • 카카오맵 위에 최단(회색)·안심(노란색) 경로를 실제 도로 곡선 그대로 함께 표시
  • 장소 검색창, 장소 정보 카드, 출발/도착 바, 경로 카드, 검색 기록 구현
  • 도착지만 정하면 현재 위치에서 출발, 확대했을 때만 가로등 마커 표시
  • PWA 적용, 휴대폰 폭 고정과 노치·홈 바(safe-area) 여백 대응

Data 포인트

  • OpenStreetMap에서 실제 도로망 그래프 생성 (노드 약 3,630개 · 간선 약 5,890개)
  • 성남시 보안등 공공데이터와 횡단보도 좌표를 가공해 위험도 계산에 반영
  • 서버 시작 시 CSV를 DB에 자동 적재, CSV가 바뀐 경우에만 다시 적재

개발하면서 겪은 문제와 해결

계산된 경로를 카카오맵 화면과 비교해 보면서, 실제 길과 다르게 가는 경로를 찾아 고쳤습니다.

문제원인해결
학교 쪽으로 가는 경로가 남쪽 교차로까지 크게 돌아서 나왔습니다. 카카오맵에서는 바로 건너가는 길이었습니다. 공개 지도 데이터(OpenStreetMap)에서 학교 안 도로와 큰길이 끊겨 있었습니다. 횡단보도 건너편 15m 안에 끊긴 길이 있으면 이어 주도록 했습니다. 경로가 600m에서 466m로 줄었습니다.
보도에 올라온 위험 제보 1건 때문에 15m 옆 학교 도로 120m 전체가 위험 구간이 되어, 안심경로가 돌아갔습니다. 제보 위치에서 25m 안에 있는 모든 길에 위험도를 반영하고 있었습니다. 제보 위치에서 가장 가까운 길에만 반영하도록 바꿨습니다.
안심경로가 최단경로보다 거리가 더 짧게 표시되는 경우가 있었습니다. 최단경로를 거리 그대로가 아니라 도로 종류별 가중치를 곱한 값으로 계산하고 있었습니다. 안심경로가 최단경로 기준으로도 더 나으면 최단경로도 그 길로 안내하도록 했습니다.
팀 프로젝트 · 이후 수업 과제로 개선

PROJECT 02

냉장고 요리사

냉장고 사진을 찍으면 AI가 재료를 인식하고, 알레르기를 고려해 레시피를 추천하는 모바일 앱

기간
2026.05 ~ 06 (팀) · 2026.06 ~ 10 (개인 개선)
인원
3인 팀, 개선은 개인
역할
초기 구조 설계, 이후 수업 과제로 사용성 평가와 개선
스택
Flutter · Spring Boot · Spring Security(JWT) · Oracle · Gemini
GitHub (개인 개선) GitHub (팀 원본)

사용성 평가 후 개선 (수업 과제)

다른 과목에서 기존 앱의 개선점을 찾아 직접 개선하는 과제가 있어서, 팀 프로젝트로 만들었던 이 앱을 대상으로 정했습니다. 닐슨의 사용성 평가 기준(휴리스틱)으로 13개 화면을 평가해 문제점과 개선 방안을 정리하고, 우선순위가 높은 1~8번을 개인 저장소에서 고쳤습니다.

문제분석이 얼마나 걸리는지 표시가 없어서 기다리는 동안 멈춘 건지 알 수 없었습니다.

수정상단에 4단계 진행 표시를 넣고, 분석 중에는 업로드 진행률과 경과 시간, 취소 버튼을 보여주도록 했습니다. 다른 탭에 갔다 와도 분석 상태가 유지됩니다.

문제알레르기를 쉼표로 직접 입력하는 방식이라 오타가 나면 필터링이 안 될 수 있었습니다.

수정목록에서 고르는 방식으로 바꾸고, 목록에 없는 재료만 따로 입력하게 했습니다. 선택한 재료는 추천 레시피에서 빠집니다.

문제레시피에 필요한 재료 중 무엇이 냉장고에 있는지 알 수 없고, 장바구니에 담으려면 직접 다시 입력해야 했습니다.

수정재료마다 보유·부족을 표시하고, 부족한 재료를 버튼 하나로 장바구니에 담을 수 있게 했습니다.

Frontend 포인트

  • 스캔 흐름을 단계별 위젯으로 분리 (선택 → 미리보기 → 분석 → 검토 → 완료)
  • 회원가입 필드별 실시간 검증, 알레르기 칩 선택과 자동완성
  • 냉장고 목록 정렬(임박순·이름순·최근순)과 유통기한 임박 배지, 첫 실행 온보딩
  • 유통기한 3일·1일 전 로컬 푸시 알림과 매일 오전 9시 리마인더

Backend 포인트

  • AI 인식 결과를 바로 저장하지 않고 사용자가 검토·확정한 뒤 저장하도록 설계
  • 알레르기 키워드 매칭: 한 글자 키워드(게·밀·콩·굴)는 재료명 맨 앞에서만 매칭해 오탐 감소
  • 북마크하지 않은 추천 레시피는 15개까지만 유지하는 자동 정리
  • 아이디·이메일 실시간 중복 확인 API, JWT 인증
수업 과제 · 개인 · AI 코딩 도구 활용

PROJECT 03

Delay Detective

미루는 일을 감지하고, AI가 왜 미루는지 물어본 뒤 작은 단위로 다시 쪼개주는 할 일 앱

기간
2026.05 ~ 06 (6주)
인원
개인
역할
AI 코딩 도구(Claude Code)로 개발. 작업 지시, 기술 결정, 실행·테스트로 검증
스택
Flutter · Provider · Hive · Firebase · Groq(Llama 3.3) · Playwright
GitHub

Backend 포인트

  • 오프라인 우선 동기화: 변경은 먼저 Hive에 저장하고 큐에 쌓은 뒤, 연결되면 Firestore로 업로드 (실패 시 다음 연결에 재시도)
  • 충돌 시 updatedAt을 비교해 나중 수정값 채택 (Last-Write-Wins), 단위 테스트로 검증
  • 기술 선택 근거를 ADR 3건으로 문서화 (프레임워크 · 상태 관리 · 저장소)

Frontend 포인트

  • 마감이 지난 미완료 일을 자동 감지해 목록 맨 위로 정렬, 감지 버그 3건 수정
  • AI 3턴 인터뷰 채팅 → 원인 분석 → 하위 태스크 적용 흐름
  • domain / data / application / presentation 계층 구조로 정리

AI · Test 포인트

  • Playwright E2E(로그인 · 이동 · 태스크 · 전체 흐름)와 단위 테스트 작성

개발하면서 겪은 문제와 해결

코드와 문서 초안은 AI가 만들었고, 저는 AI에게 작업을 나눠 지시하고 결과물을 검토해 기술을 결정했습니다. 앱을 직접 실행하고 자동화 테스트를 돌리면서 문제를 찾았습니다.

문제원인해결
자동화 테스트(Playwright)에서 할 일 제목을 입력한 뒤 화면 아래쪽 저장 버튼을 눌러도 아무 반응이 없었습니다. Flutter Web은 화면을 캔버스에 그리는데, 글자를 입력하는 동안 숨겨진 입력창이 포커스를 잡고 있어서 본문 영역 클릭이 앱에 전달되지 않았습니다. 입력 후에도 눌리는 상단 바에 저장(체크) 버튼을 추가하고, 채팅 입력은 Enter로 보낼 수 있게 바꿨습니다.
AI 응답에 한자·일본어·러시아어가 섞여 나오는 경우가 있었습니다. 사용한 언어 모델이 한국어 답변 중간에 다른 언어를 섞어 쓰는 경우가 있었습니다. 응답을 받은 뒤 한국어가 아닌 문자를 지우는 처리를 넣었습니다.
